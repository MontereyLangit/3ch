# Shift_JIS → encoding-japanese へ移行する詳細設計

作成日: 2025-10-25  
作成者: 設計案 (mmr-3ch 向け)

目的
----
現在の実装では独自の Shift_JIS ↔ UTF-8 変換（リポジトリ内の `sjis` ラッパや自前の percent-decoding 実装）が原因で、特定の2ch専用ブラウザ（特に絵文字やベンダー依存のバイト列を含むケース）で絵文字が消える・エラーになる等の不具合が発生しています。

これらを解消するために、独自実装を廃止し、実績のあるパッケージ `encoding-japanese` を用いて Shift_JIS <-> Unicode の変換処理を行う設計を示します。これにより、絵文字や拡張文字の扱いが改善されることを目指します。

対象範囲
-------
- 主に影響するファイル（現状）:
  - src/bbs.cgi.js
  - src/common.js（もし `sjis` クラスをここで提供しているなら更新または除去）
- 変更箇所の関数（bbs.cgi.js 内）:
  - readForm() 内で利用されている decodeSjisURIComponent()
  - processTrip() の SJIS エンコード（現在 `new sjis().encode()` を利用している箇所）
- 付属：package.json に依存追加 (encoding-japanese)

設計方針
--------
1. "自前の SJIS 変換" を無くし、すべて `encoding-japanese` を用いて行う。
2. percent-encoded の文字列（POST の body 中のパラメータ）を安全にバイト列へ復元し、そのバイト列を `encoding-japanese` に渡して Unicode 文字列を得る。
3. processTrip 等で「SJIS のバイト列を 1バイトごとの JS 文字列に変換して処理」している箇所は、同等のバイト列を生成 (Uint8Array) して既存ロジックと互換性を維持する。
4. 互換性確保のため、`encoding-japanese` が使えない場合のフォールバック（可能なら既存簡易実装）を用意する。ただし本番では常にパッケージを使用する想定。
5. 単体テストと受入テストで、既知の絵文字テストベクター、Monazilla から来るケース、その他境界値（不完全な % エンコード等）を検証する。

依存関係
--------
- 新規依存: encoding-japanese
  - 推奨バージョン: ^2.0.0（実際の最新を採用）
  - package.json に追加
  - ビルド/デプロイ環境（Cloudflare Workers 等）で npm モジュールが使える前提。もしバンドルが必要ならビルド時に bundle（esbuild/rollup）する。

設計詳細
--------

A. percent-encoded → バイト列の安全な復元
- 現行 decodeSjisURIComponent は「%XX → byte、それ以外は charCodeAt」で済ませている。これを改善し、
  - '+' はスペースに変換（既に外側で行われている場合は統一）
  - `%` の後に2桁の16進があればそのバイトを push
  - `%` の後に不正なシーケンスが来た場合は '%' と続く文字を「そのままのバイト列」として扱う（もしくは U+FFFD にフォールバック）
  - 非 `%` の ASCII 文字は `charCodeAt` を 1 バイトとして扱う（既存の互換性を維持）
- 結果は Uint8Array にする。

B. encoding-japanese の使用方法（概念）
- encoding-japanese は JS での文字コード変換用ライブラリ。一般的な使い方：
  - var unicodeCodes = Encoding.convert(uint8array, { to: 'UNICODE', from: 'SJIS' });
  - var str = Encoding.codeToString(unicodeCodes);
- processTrip のように "SJIS バイト列を 1バイトずつ JS 文字列にして crypt に渡している" 箇所は、`Encoding.convert( <unicode string> , { to: 'SJIS' })` ではなく、逆に「入力(tripKey) を SJIS バイト列にエンコード」してから String.fromCharCode(...bytes) 相当の 1バイト/文字の JS 文字列を作る必要がある（既存ロジック互換のため）。

C. 具体的な置換方針（bbs.cgi.js）
- 1) ファイル冒頭に import 追加：
  - import Encoding from 'encoding-japanese';
  - 既存で `sjis` を common.js から import している場合は、その利用箇所を置換し、common.js 側の sjis export は将来的には削除または互換ラッパにする。
- 2) decodeSjisURIComponent の差し替え（旧実装を置換）
  - 新実装（擬似コード）:
    ```
    function decodeSjisURIComponent(encodedURIComponent) {
      // 1) '+' -> ' '
      const s = encodedURIComponent.replace(/\+/g, ' ');

      // 2) build bytes array
      const bytes = [];
      for (let i = 0; i < s.length; ) {
        if (s[i] === '%' && i + 2 < s.length && /^[0-9A-Fa-f]{2}$/.test(s.substr(i+1,2))) {
          bytes.push(parseInt(s.substr(i+1,2), 16));
          i += 3;
        } else {
          // unescaped ASCII -> treat as single byte
          bytes.push(s.charCodeAt(i) & 0xFF);
          i++;
        }
      }
      const u8 = new Uint8Array(bytes);
      // 3) convert SJIS bytes -> Unicode code points (array)
      const unicodeCodes = Encoding.convert(u8, { to: 'UNICODE', from: 'SJIS' });
      // 4) to JS string
      return Encoding.codeToString(unicodeCodes);
    }
    ```
  - 不正な `%` シーケンスへのポリシーは「可能なら復号し、無効なら '%' をそのまま扱う」で設計（テストで確認）。
- 3) processTrip 内の変更
  - 既存:
    ```
    const sjisEncoder = new sjis();
    const sjisBytes = sjisEncoder.encode(gb.tripKey);
    const handlePass = String.fromCharCode(...sjisBytes);
    ```
  - 置換:
    ```
    // セット: gb.tripKey は既に JS 文字列 (Unicode) として渡される前提
    // 1) Unicode string -> SJIS bytes
    const sjisBytesArray = Encoding.convert(gb.tripKey, { to: 'SJIS', from: 'UNICODE' });
    // sjisBytesArray が数値配列なのでそのまま String.fromCharCode 相当で1byte-per-charの文字列にする
    const handlePass = sjisBytesArray.map(code => String.fromCharCode(code & 0xFF)).join('');
    ```
  - 以後の処理（正規表現、hex/crypt等）は既存ロジックのまま使えるはず（既存コードは handlePass の各バイトを想定している）。
- 4) 既存 common.js の `sjis` クラス対応
  - common.js 内で `sjis` を export しているなら、互換のラッパを残しつつ内部では encoding-japanese を使うように変更することを推奨。これにより、リポジトリ内の他箇所の修正コストを下げられる。
  - 例: `export class sjis { encode(str){ const arr = Encoding.convert(str, { to:'SJIS', from:'UNICODE'}); return arr; } decode(bytes){ ... } }`
  - ただし設計段階では bbs.cgi.js 側に直接 import する方針でも良い（段階的移行）。

D. フォールバック / エラーハンドリング
- Encoding の呼び出しを try/catch で包む。失敗時は:
  - ログ出力（環境に応じた logging）。
  - 旧実装（現在の decodeSjisURIComponent のロジック）を用いるフォールバックを行う（ただし絵文字消失のリスクはある）。
  - 必要ならリクエストをエラーにして（dispError）ユーザ向けに説明する（ただし可用性重視ならフォールバック推奨）。
- `encoding-japanese` の機能が本番環境で利用可能であることはデプロイ前に確認（バンドル / worker ランタイム対応）。

E. テストケース
- 単体テスト（必須）
  1. 単純な日本語（Shift_JIS エンコード） -> 正しくデコードされること。
  2. 半角英数字のみの値（混在） -> 正常に処理されること。
  3. 絵文字（携帯絵文字、SoftBank/Docomo/au 系）を含む SJIS データ -> Unicode に変換され絵文字が失われないこと（期待される Unicode 絵文字へ変換される/もしくは適切に置換される）。
  4. 不正な % エンコード（例: "%GZ", 末尾に "%"） -> フォールバックポリシーに従う挙動（テスト期待値を明確に）。
  5. processTrip における 12バイト/10バイトトリップの既存ベクターで結果が現行実装と互換であること。
  6. Monazilla からの Submit の判定（gb.isSJIS の挙動）を維持する回帰テスト。
- 結合テスト（ステージング）
  - Monazilla（Shift_JIS を送る専ブラ）からの投稿シミュレーション（絵文字含む）
  - ブラウザ(UTF-8) からの投稿（今までと同じ挙動）
  - スレ作成、返信、subject 更新など一連の投稿フローを通す
- 受入テスト（運用側）
  - 実機（可能なら実際に絵文字を送れる Android/iOS 専ブラ）で確認
  - ログに絵文字が含まれているか、エラーが発生していないか監視

F. 性能・運用面
- 文字コード変換の CPU 負荷は若干増える可能性があるが、POST 単位の処理であり大幅なボトルネックにはならない想定。必要なら変換処理のホットパスをキャッシュする案を検討（同一文字列の頻出は稀）。
- 変換処理を try/catch にしている分、失敗時の処理で若干遅延するが、正常フローへの影響は限定的。
- 監視ポイント:
  - 変換例外の頻度（ログ）
  - 投稿エラーの増加数
  - レイテンシ（平均）

H. 具体的なコード例（bbs.cgi.js 内の差し替え候補）
- 1) import 追加（ファイル上部）
  ```javascript
  import Encoding from "encoding-japanese";
  // 既存: import { sjis, ... } from "./common.js";
  // common.js 側の sjis は将来のために残すか互換ラッパ化
  ```

- 2) decodeSjisURIComponent（置換関数）
  ```javascript
  function decodeSjisURIComponent(encodedURIComponent) {
    const s = encodedURIComponent.replace(/\+/g, " ");
    const bytes = [];
    for (let i = 0; i < s.length; ) {
      if (s[i] === '%' && i + 2 < s.length && /^[0-9A-Fa-f]{2}$/.test(s.substr(i+1,2))) {
        bytes.push(parseInt(s.substr(i+1,2), 16));
        i += 3;
      } else {
        // treat unescaped ASCII as a single byte
        bytes.push(s.charCodeAt(i) & 0xFF);
        i++;
      }
    }
    try {
      const u8 = new Uint8Array(bytes);
      const unicodeCodes = Encoding.convert(u8, { to: "UNICODE", from: "SJIS" });
      return Encoding.codeToString(unicodeCodes);
    } catch (e) {
      // フォールバック: 旧実装風に処理して返す（ログ出力を推奨）
      // ここでは単純に ascii 変換して返す
      return String.fromCharCode(...bytes);
    }
  }
  ```

- 3) processTrip の SJIS エンコード部
  ```javascript
  // gb.tripKey は既に JS の Unicode 文字列
  const sjisBytesArray = Encoding.convert(gb.tripKey, { to: "SJIS", from: "UNICODE" });
  const handlePass = sjisBytesArray.map(n => String.fromCharCode(n & 0xFF)).join('');
  ```

注意事項 / 補足
----------------
- encoding-japanese のマッピングが期待通りに携帯キャリアの絵文字（一部ベンダー独自）を Unicode に変換するかは、実地での確認が必要です。もし特定ベンダー依存の絵文字が依然問題になる場合、専用の絵文字マッピングテーブルを別途用意して `encoding-japanese` の出力後に補正するアプローチを検討してください。
- Cloudflare Workers 環境など、外部モジュールのバンドリングに制約があるランタイムの場合、ライブラリをバンドルして Worker にアップロードする方式を取る必要があります（CI でのビルド確認必須）。
- 既存の `sjis` クラス（common.js）をすぐに削除すると他箇所に影響する可能性があるため、当面は互換ラッパを提供する方が安全です。最終的にはリファクタで sjis クラスを削除して依存を一本化することを推奨します。
