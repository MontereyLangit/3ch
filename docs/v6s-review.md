## Codex CLI

`codex exec --sandbox read-only` で実行。実行モデルは `gpt-6-astra`。
コード送信について利用者の明示的な許可を取得して実行。

> 補足: 初回は `codex exec` が stdin を待って無応答のままだった。`< /dev/null` で解決。

| 指摘 | 判断・対応 |
| --- | --- |
| **[高]** R2 モックが実 API に無い `onlyIf.doesNotExist` を実装。失敗時の戻り値も実際は `null`。ETag 条件付き書き込みを削除してもテストが通る | **採用。** オラクルとして機能していなかった。実 API に合わせ、競合を注入するテストを追加。この過程で**本番側の「不在時のみ作成」ガードが実際には何も守っていない**ことが判明し、**KB-25** として記録 |
| **[高]** ID・識別ID のテストが同一実装の自己比較で、ハッシュの連結順・salt・日付窓が変わっても通る | **採用。** 移植の等価性検証として無意味だった。時刻を固定した具体値に置換し、JST 日付境界・IPv6・`BBS_ID_GROUP`/`RESET` のケースを追加 |
| **[中]** 304 テストがミリ秒の偶然に依存して将来落ちうる。`Last-Modified` の由来を説明したコメントが誤り | **採用。** ミリ秒を明示的に固定し、ms≠0 と ms=0 を別ケースに分離。コメントは実コードを読んで訂正（`modifiedAt` 由来、dat 解析はフォールバック）。**台帳 KB-23 の記述自体は正しく、誤っていたのはテストのコメントのみ**だった |
| **[中]** dat の比較が `split('\n').filter(Boolean)` で末尾改行の欠落を隠す。メール欄が空になる検証を空入力で行っており、保存する実装に変わっても通る | **採用。** 全文一致に変更し、メール欄に `sage` を入れて KB-10 を非空入力で固定 |
| **[中]** トリップが ASCII 中心で KB-14 の二重エンコードが通常のバイトハッシュに変わっても検出できない。キャップが全て `!` 付きで通常経路を通らない | **採用。** 11/12バイト境界の日本語キーと `+`→`.` を含む例、非 `!` のキャップ経路を追加 |
| **[中]** Shift_JIS のバイト期待値を検証対象のエンコーダ自身で生成しており自己参照。Range テストがボディを検証していない | **採用。** 固定バイト列に置換し、Range テストにボディのバイト比較を追加 |
| **[中]** `BBS_LIVE` の90%強制sage分岐が未カバー | **採用。** 乱数を閾値の両側で固定し、板内順序と headline 更新の有無を検証 |

7件すべて妥当と判断し、却下したものは無い。

## Gemini CLI

`gemini --approval-mode plan -p` で実行。Codex がテスト側を見たため、Gemini には
**Scala 移植の等価性**（JS と Scala の言語差、Scala.js 固有の罠）を中心に依頼した。
コード送信について利用者の明示的な許可を取得して実行。

> **注意: このレビューは Shift_JIS を `encoding-japanese` へ移行する決定より前の状態に対するもの。**
> 観点3（変換表の扱い）の評価は、その後の方針変更により前提が変わっている。

| 指摘 | 判断・対応 |
| --- | --- |
| `HexToBinary` の非16進入力が JS と非等価（JS は `NaN`→`\x00`、Scala は例外） | **既知。** 移植方針 R-07 として記録済み。現状呼び出し元から到達しないため意図的な差異として許容し、呼び出し元の移植時に到達可能性を再確認する |
| **golden の `sha1base64.json` に高位バイト（0x80〜0xFF）を含む文字列が無く、KB-14 の二重エンコードを実質的に縛れていない** | **採用。** 本番パイプラインで実際に起きる入力が抜けており、通常のバイトハッシュに変えても検出できない。Shift_JIS 差し替え作業の完了後に golden へ追加する |
| `sjis-encode.json` に孤立サロゲートの境界値が無い | **採用。** ただし Shift_JIS 実装の差し替えと重なるため、差し替え後の実装に対して追加する |
| `UnixCrypt.cryptBytes`（配列版）のテストが未実装 | **採用。** golden 追加とあわせて対応 |
| `String.replace` の取り違え、MD5/DES のビット演算・オーバーフロー、`undefined` の番兵表現、文字列長の単位 | **問題なしとの評価。** 特に `crypt` のソルト1文字時に `undefined == 0` が偽になる挙動を負の番兵で再現した点（KB-26）を妥当と評価。今後 `bbs.cgi` 移植時の KB-03（`replace` 単発置換）に要警戒という指摘は移植方針 R-03 に既出 |
| 変換表を実測ダンプで固定した判断は妥当。ただし Node と workerd で `TextDecoder('sjis')` が同一である必要があり、実機の差分テストによる裏付けが必須 | **前提が変わったため対応不要。** 利用者の指示により Shift_JIS は `encoding-japanese` へ移行することになり、変換表がランタイム由来でなくなるため本リスク（R-06）は解消する |
| `SjisDecodeError` が JS の `TypeError` と型が異なる | **前提が変わったため対応不要。** `encoding-japanese` への移行で decode は例外を投げなくなる（KB-18 の解消） |

## 2026-09-23 引き継ぎ後のセルフ確認 — Shift_JIS 移行停止

- v5 の実装とローカルの encoding-japanese を直接呼び、変換表9,027件の decode を再比較。
  1,513件の差異（正常な文字10件、制御コード3件、未割当位置1,500件）を確認した。
- 正常な文字10件の encode も実測。例: `≒` は v5 の `87 90` に対し `81 E0`。
  `87 90` の decode は v5 の `≒` に対し `?`。KB-04/17/18 では説明できない。
- **判断・対応:** 引き継ぎ §3.2(A) の明示的な停止条件に従い、差し替えと後続の移植を停止。
  既存 JSON の想定外差異を許容例外として採用しない。
- 詳細と検証範囲は [sjis差異一覧.md](sjis差異一覧.md)。表外の全入力を網羅したとは主張しない。
- 実装変更なし。今回は比較の実行のみで、npm / sbt の全テストおよび外部 CLI レビューは未実施。
