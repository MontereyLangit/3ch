# 01. 現行 v5 の課題（Step 4 / 5 仕様検討の起点）

Step 4（フロントエンド Next.js 化）・Step 5（新仕様バックエンド + bg + DB 変更）の要件を決める前提として、
現行 v5 の課題を整理する。各項目は「課題（運営側の認識）」と「コード上の裏付け」を分けて書く。
裏付けの行番号は `develop_v6s`（`8185a00`）時点。

---

## 1. パフォーマンス

### 課題
- 専ブラ読み込みは速くはなく、書き込みは遅い。
- Cloudflare Workers 上の 2ch 型掲示板が増えたことで、求められる水準が上がっている。
  **読み込み・書き込みとも 1 秒未満、コンマ秒単位**が必要。
- 原因は v5 設計時のストレージ利用方針の誤り。R2 書き込みなどがボトルネック。

### コード上の裏付け

**書き込み（`src/bbs.cgi.js` `onRequest`）**: 1 回の投稿で、次のストレージアクセスが**すべて直列**に走る。

| # | 処理 | アクセス先 | 箇所 |
| :-- | :-- | :-- | :-- |
| 1 | キャップ照合（キャップ入力時のみ） | KV `CAP` get | `bbs.cgi.js:372` |
| 2 | 板設定 `SETTING.TXT` | R2 get | `bbs.cgi.js:452` |
| 3 | スレ dat・スレ設定 | Thread DO | `bbs.cgi.js:483-` |
| 4 | 規制ルール `deny.cgi` → `ngwords.cgi` | R2 get × 2（直列） | `moderation.js:22-23` |
| 5 | レス追加（dat + log を丸ごと put） | Thread DO → **Board DO へ連鎖呼び出し** | `thread.js:161-177` |
| 6 | subback 更新 | **R2 get + put** | `bbs.cgi.js:775, 818/824` |
| 7 | 過去ログ目次更新（スレ落ち発生時） | **R2 get + put** | `bbs.cgi.js:791, 807/811` |
| 8 | 全体ヘッドライン `headline.txt` 更新 | **R2 get + put** | `bbs.cgi.js:844, 871` |

- 毎回の投稿で、R2 への read-modify-write が最低 2 回（subback・headline）ある。R2 は書き込みのレイテンシが大きい。
- 同時投稿への対策は ETag 条件付き put（`onlyIf: etagMatches`）。競合したときの挙動は次のとおり。
  - subback: 「板飛びそうなので、またの機会にどうぞ。。。」エラーを返す（`bbs.cgi.js:816, 821, 828`, **KB-27**）。
    **レスは直前に Thread DO へ追加済み**なので、利用者にはエラーと表示されるのに書き込みは成立している。
  - headline: 競合した更新は黙って捨てられる（`bbs.cgi.js:870`）。
  - 板の書き込みが活発なほど競合が増え、エラー率が上がる。
- 板設定・規制ルールは投稿のたびに R2 から読み直している（キャッシュなし）。
- Thread DO は投稿ごとに dat 全体・log 全体を 1 値として put する。スレが伸びるほど書き込み量が増える（1000 レス近くで数百 KB）。

**読み込み（`src/main.js`）**
- dat・subject.txt・headline は `cache-control: no-store`（`main.js:163, 222`）で、エッジキャッシュが効かない。
  毎回 DO / R2 に届き、Shift_JIS 変換を dat 全体に対してやり直している。
- `headline.txt` の配信では、**行ごとに Board DO `getRemoved()` を直列で呼ぶ**（`main.js:148`、N+1 問題）。

### Step 5 への含意
- 投稿時に同期で行う処理を「Thread DO への追記」だけにし、subback・headline・過去ログ目次の更新は
  **`bg`（バックグラウンドサービス）/ Queue へ非同期化**する。
- 板設定・規制ルールをメモリ / Cache API / DO 内に保持し、投稿のたびに R2 を読まないようにする。
- dat はレス単位の追記型ストレージ（DO SQLite など）にする。読み込み側は Shift_JIS 変換済みバイト列のキャッシュと
  Range 差分配信を組み合わせる。

## 2. 絵文字・文字コード

### 課題
- v5 は絵文字の扱いに不具合がある。UTF-8 で書き込んだ絵文字が見えなくなる、など。

### コード上の裏付け（既知不具合台帳 KB-04 / KB-17 / KB-18）
経路によって挙動が異なる。

| 書き込み経路 | 保存（DO 内 dat） | Web（UTF-8 出力） | 専ブラ（Shift_JIS 出力） |
| :-- | :-- | :-- | :-- |
| Web から絵文字を生で投稿（UTF-8） | 絵文字のまま保存 | 表示される | **NUL バイト `0x00` に化ける**（KB-17）→ 見えない / 専ブラによっては行が壊れる |
| 専ブラから NCR（`&#128512;`）で投稿 | NCR のまま保存（`bbs.cgi.js:276` が `&#…;` をエスケープしない） | ブラウザが NCR を解釈すれば表示される | NCR のまま届き、専ブラが解釈すれば表示される |

- 「UTF-8 で書き込んだ絵文字が見えなくなる」のは、**保存時ではなく Shift_JIS 出力時の欠落**。データは DO に残っている。
- ほかに、IBM 拡張行（`0xF0`–`0xFC`）が変換テーブルにない（KB-04）。未対応バイトを decode すると TypeError になる（KB-18）。
- なお Step 3 の Scala.js 版では、KB-17 を NCR フォールバックに置き換え済み（`docs/sjis差異一覧.md`）。

### Step 5 への含意
- 内部表現は UTF-8（Unicode）に統一し、Shift_JIS は専ブラ向けの出力時だけ変換する。
  未対応文字は NCR にフォールバックする。
- v5 の DO に残っている絵文字データは移行時にそのまま引き継げる（壊れているのは出力だけ）。

## 3. 認証がない

### 課題
- 2023 年の大規模スクリプト荒らし以降、2ch 型掲示板では認証が必須になった。認証のない掲示板には避難も移住もされない。
- v3 には認証があった。
- 認証がないため自演への耐性も低く、これも移住が敬遠される要因になっている。

### コード上の裏付け
- 投稿者の識別は IP・UA・端末情報ヘッダ（`x-ch3-device-information`）から作る ID / 識別 ID だけ（`bbs.cgi.js:76-80, 199-204`）。
- Cookie は読んでいる（`bbs.cgi.js:557`）が、発行・検証を伴う認証フローはない。
- 「猿」系処理（`processCommandsAndByBySaru`）はコメントアウトされている（`bbs.cgi.js:155`）。

### Step 5 への含意
- 書き込み認証（Cookie / トークン発行型）を DB 変更込みで設計する。
- 認証済みトークン単位の識別と自演検知を規制と連動させる（→ 4 章）。

## 4. 規制が v3 や他掲示板と比べて脆弱

### 課題
- 荒らしに弱く、運営に支障が出ている。

### コード上の裏付け（`src/moderation.js`, 41 行）
- 判定は `deny.cgi` / `ngwords.cgi` の正規表現ルールを順に当てるだけ。Tor（`country === 'T1'`）だけ固定で拒否する。
- 連投規制・スレ立て規制・時間窓のレート制限・認証単位の規制・自動規制（bg による集計）はない。
- ルールは投稿のたびに R2 から読んで parse している（1 章と同じ問題）。

### Step 5 への含意
- レート制限・連投規制を DO（板単位 / 認証トークン単位）で持つ。
- bg で投稿ログを集計して自動規制し、管理画面から即時反映できるようにする。

## 5. v3 と比べて機能が大幅に少ない

### 課題
- **SETTING コマンド**（ID 無しスレなど、スレ単位の設定をスレ立て時に指定する機能）がない。
  v3 時代に 3ch を大きく盛り上げた 3ch 文化だったが、v5 では立てられない。
- 検索機能・新着レス一覧などもない。

### コード上の裏付け
- Thread DO に `settings`（スレ設定）の置き場はあり、スレ立て時に初期値を書いている（`thread.js:173`, `bbs.cgi.js:740` 付近）。
  ただ、利用者がコマンドで設定を変える経路はない（コマンド処理はコメントアウト）。
- 検索・新着一覧に使える索引ストレージがない（dat は DO ごとに分散していて、横断して検索できない）。

### Step 5 への含意
- SETTING コマンドを v3 互換で復活させる（v3 の実装を参照して仕様を洗い出す）。
- 検索・新着レス一覧は、bg が投稿イベントを受けて索引（D1 / 外部検索など）を更新する方式にする。

---

## 6. Web 版がレガシーかつ重い

### 課題
- 2000 年代のレガシー SPA。非同期処理になっていないため重く、機能も非常に少ない。
- SEO が非常に悪く、ライトユーザーが寄り付かない要因になっている。
- v3 / v4 時代は独自 JS で多機能化していた。軽くはなかったが、比較的好評だった。

### 補足
- Web 版（`3chiko.html`）は別リポジトリ（`ch3/3chiko`）。Step 3 までは変更しない前提。

### Step 4 への含意
- Next.js で SSR / SSG を使い、スレ・板一覧を検索エンジンに読ませる。
- v3 / v4 独自 JS の好評だった機能を棚卸しし、新 UI に取り込む。新 UI は `../v6/docs/3ch_ui/` の画面モックのうち**利用者画面（read.cgi・板top 等）のみ**を参考にする。管理画面・bg の画面は参考にしない。
- Step 4 は「DB 変更なし」の制約がある。検索・新着一覧など DB 変更が必要な機能は、Step 5 と同時に出すか段階的に出すかを決める必要がある。

## 7. 板一覧に使われていない板が残る

### 課題
- 板一覧（bbsmenu）に、使われていない板が残り続ける。掲示板全体が廃れた印象になる。
- 管理画面から、表示するかどうかの閾値を決められることが望ましい。

### コード上の裏付け
`/bbsmenu.html` の生成経路は 2 つある（`main.js:40-`）。

| 経路 | 条件 | 挙動 |
| :-- | :-- | :-- |
| 手動 | R2 に `bbsmenu.html` がある（管理画面 `/admin/menu` で保存） | 保存した HTML をそのまま返す。板の追加・削除はすべて手作業 |
| 自動 | R2 に `bbsmenu.html` がない | `headline.txt` の全行（最大 300 板）をそのまま列挙する |

- 自動経路は、`headline.txt` の各行に入っている最終更新時刻（第 3 フィールド）を**使っていない**。
  一度でも age 書き込みがあった板は、300 板の枠から押し出されるまで一覧に残り続ける。
- `headline.txt` は age 書き込みでしか更新されない（`bbs.cgi.js:841` sage なら更新しない）。
  そのため、sage でしか使われていない板は「最終更新」が古いまま扱われる。
- 表示条件を設定する仕組み（閾値・手動の表示 / 非表示指定・カテゴリ）はない。

### Step 5 への含意
- 板のメタ情報（最終書き込み時刻・期間内の書き込み数・表示状態・カテゴリ）を、DB 上の板マスタとして持つ。
  最終書き込み時刻は sage も含めて記録する。
- 管理画面で閾値（例: 「N 日書き込みなし」「直近 N 日の書き込み数 M 未満」）を設定し、bg が定期的に表示状態を更新する。
  強制表示・強制非表示の手動指定を閾値より優先する。
- 一覧から外すのは表示だけで、板そのもの（URL・dat・専ブラからのアクセス）は生かす。
- 専ブラ用の bbsmenu と Web 版（Step 4）の板一覧は、同じ判定結果を使う。
- 閾値・板ごとの強制表示 / 非表示を設定する管理画面 UI は、v6 モックを参考にせず別途設計する
  （v6 モックで参考にするのは利用者画面のみ）。

## 課題 × Step 対応（暫定）

| 課題 | Step 4（Front, DB 変更なし） | Step 5（Back + bg, DB 変更あり） |
| :-- | :-- | :-- |
| 1. パフォーマンス | Web 側のみ（SSR・キャッシュ） | **主対象**（非同期化・ストレージ再設計） |
| 2. 絵文字・文字コード | 表示側で対応 | **主対象**（出力変換の修正） |
| 3. 認証 | 認証 UI | **主対象** |
| 4. 規制 | 管理 UI | **主対象** |
| 5. 機能不足 | UI（検索・新着・SETTING） | 索引・コマンド処理 |
| 6. Web 版 | **主対象** | SSR 用 API |
| 7. 休眠板の表示 | 板一覧 UI・管理 UI（閾値設定） | **主対象**（板マスタ・bg による判定） |

- Step 4 と 5 のリリース順序（DB 変更が要る機能の扱い）。
- 休眠板の閾値の指標（最終書き込みからの日数か、期間内の書き込み数か、両方か）と、非表示にした板を見せる手段（「その他の板」欄など）を用意するか。
