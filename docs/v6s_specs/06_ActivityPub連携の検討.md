# 06. ActivityPub 連携とリアクション機能の検討（将来構想）

2026-09-26 検討。**将来の構想**として、3ch を ActivityPub（以下 AP）のネットワーク（Fediverse）とつなぐ方策と、
その前提になる Misskey 風の機能（リアクションなど）を検討する。
実装時期は Step 5（新バックエンド + DB 変更）以降で、本書の目的は **Step 5 の DB 設計より前に決めておくべきこと**を洗い出すことにある。

## 結論（案）

- **連携は段階的に進める。最初は「3ch → Fediverse への一方向の公開」だけにする。**
  板を AP の `Group` アクターとして公開し、Mastodon / Misskey などから板をフォローすると、新スレ（と任意でレス）がタイムラインに流れる形にする。
  外部からの書き込み（リプライの取り込み）は最後の段階とし、モデレーションの自動化が整うまでは入れない（下記 5 章）。
- **設計は「Threadiverse」の事実上の標準に合わせる。** 板 = `Group`（FEP-1b12）、スレ = 会話コンテキスト（FEP-7888 / FEP-171b）、
  レス = `Note`。NodeBB・Lemmy・PieFed・Mbin と同じ形にしておけば、個別対応なしで相互に読める。
- **リアクションは 3ch 内の機能として先に作り、AP とは後でつなぐ。**
  匿名のままリアクションでき、専ブラの dat には一切影響しない（dat の 5 フィールドは変えない）。
  AP 側は `Like`（+ `content` 付き）/ `EmojiReact`（FEP-c0e0）で受け取り、Misskey・Pleroma 系のリアクションと互換にする。
- **匿名性と AP の「投稿者 = アクター」モデルの衝突が最大の論点。**
  名無しの投稿は、板の日替わりの識別 ID ごとの**使い捨てアクター**として表現する案を推す（下記 3.2）。
  v6 では ID を廃止し識別 ID に一本化する（`07_IDの廃止.md`）ので、識別 ID を基準にする。
  トリップ・キャップは、希望者だけ固定アクター（フォロー可能）にする。
- **連合は板ごとのオプトイン（既定オフ）。** 成人向け・グレーな板は対象外にする。
  AP で配った内容は他サーバーにコピーされ、削除が保証されないため、削除依頼・法的対応の実効性が下がる（下記 6 章）。
- **Step 5 の DB 設計前に決めておくこと**（下記 8 章）: 投稿の恒久 URL、AP 用ドメイン、リアクションの保存場所、配信キュー（bg）の枠。

## 1. なぜ検討するか

方針企画書（`docs/方針企画書_板戦略・広告戦略.md`）との関係:

| 企画書の論点 | AP 連携で期待できること | 懸念 |
| :-- | :-- | :-- |
| KSF 1: 板単位のクリティカルマス | 専門板を Fediverse から直接フォローできる。3ch に来なくても板の新スレに気づける。 | フォロワーが「3ch の住民」になるとは限らない（読むだけで終わる） |
| KSF 5: 互換エコシステムとの接続 | まとめサイトに加えて、Fediverse を二つ目の外部エコシステムにできる | — |
| 獲得チャネル: 5ch に板がない新規トピック | Fediverse の趣味コミュニティは 5ch と重ならない層で、専門板の「生える」土壌になりうる | 顕名文化の利用者と匿名文化の衝突 |
| 避難所ポジション | 平時から外部に存在を知らせる経路になる（企画書「到達可能性の確保」） | 避難イベント時の配信コスト |
| KSF 3: 1 投稿あたりの限界費用 | — | 配信（fan-out）はレスごとにコストが増える（下記 7 章） |
| KSF 4: インフラ主権と可搬性 | 3ch が落ちても、配った内容は他サーバーに残る | **AP の ID はドメインを含む。ドメインを変えると連合が切れる**（下記 8 章） |
| KSF 6: 法的耐性 | — | 配った投稿は消しきれない。外部からの書き込みの責任の所在 |

Misskey（とくに misskey.io）は日本の匿名掲示板文化と地続きの利用者が多く、日本語圏の Fediverse で最大の勢力である。
Misskey に近い機能（リアクション等）を備えることは、AP 連携しない場合でも Web 版の UX 改善（`01_現行v5の課題.md` の「v5 は UX が低い」）になる。

## 2. 他の AP 掲示板・フォーラムの調査

| ソフト | 形態 | AP 上の表現 | 3ch への示唆 |
| :-- | :-- | :-- | :-- |
| **Lemmy / Mbin / PieFed** | Reddit 型（コミュニティ + 投稿 + コメント木） | コミュニティ = `Group`。投稿 = `Page`（`name` がタイトル）、コメント = `Note`。コミュニティが `Announce` で配り直す（FEP-1b12）。投票は `Like` / `Dislike` | Threadiverse の最大勢力。これと相互に読める形にするのが最優先。Mbin は Mastodon からのコミュニティ購読にも対応 |
| **NodeBB**（v4 以降） | 伝統的フォーラム（カテゴリ + トピック + 投稿）。**2ch 型に最も近い** | カテゴリ = `Group`、投稿 = `Note`。`audience` = カテゴリ、`context` = トピック（FEP-7888）。カテゴリの `@ハンドル` 宛てに投稿すると新トピックになる。絵文字リアクション（FEP-c0e0）に対応。スレ全体の後追い取得（FEP-f228 backfill）を推進 | **主な手本**。「板 = カテゴリ、スレ = トピック（フラットな時系列）」の対応がそのまま使える |
| **Discourse**（ActivityPub プラグイン） | フォーラム | カテゴリ（・タグ）ごとにアクター。記事の公開方式として「最初の投稿だけ」と「トピック全体」を選べる（要確認: プラグインの版による） | **「スレ立てだけ配る」モード**は配信コストを抑える案として参考になる |
| **Misskey** | マイクロブログ | 投稿 = `Note`。リアクションは `Like` + `content`（絵文字）+ `_misskey_reaction`。1 投稿に 1 人 1 リアクション。引用は `_misskey_quote` / `quoteUrl`。**「チャンネル」機能は連合しない** | リアクションの互換対象。Misskey のチャンネルが連合しないのは、スレ型の場を AP に載せる難しさの表れでもある |
| **Pleroma / Akkoma / Fedibird** | マイクロブログ | `EmojiReact` アクティビティ。1 人が異なる絵文字で複数リアクション可 | FEP-c0e0 はこれらと Misskey の実装を整理したもの |
| **FChannel** | 匿名イメージボード（Go 製） | 板をアクターとして連合する。主に同じソフト同士の連合（要確認） | **匿名掲示板の AP 化の数少ない先例**。ただし一般の Fediverse との相互運用は限定的で、3ch は Threadiverse 標準側に寄せる |

| FEP | 内容 | 3ch での使いどころ |
| :-- | :-- | :-- |
| FEP-1b12 | Group による連合（`Announce` で配り直す） | 板アクター |
| FEP-7888 | `context` プロパティの意味づけ | スレ = `context` |
| FEP-171b | 会話コンテナ（会話をコレクションとして持つ） | スレのレス一覧をコレクションで公開 |
| FEP-f228 | 会話の後追い取得（backfill） | 途中からフォローした人が過去レスを取れる |
| FEP-c0e0 | 絵文字リアクション | リアクションの互換 |
| FEP-044f / FEP-e232 | 引用の承認 / オブジェクト参照（引用） | 外部からの引用。3ch 側の `>>n` は引用ではなく返信として扱う |
| FEP-521a / FEP-8b32 | アクターの鍵（Ed25519）/ オブジェクトの完全性証明 | 使い捨てアクターの鍵（3.2） |

## 3. データの対応づけ

### 3.1 板・スレ・レス

| 3ch | AP | ID（URL）の例 | 備考 |
| :-- | :-- | :-- | :-- |
| 板 `{bbs}` | `Group` | `https://3ch.io/ap/b/{bbs}` / `@{bbs}@3ch.io` | `name` = 板名（`BBS_TITLE`）、`summary` = ローカルルール（`head.txt`） |
| スレ `{bbs}/{key}` | `context`（`OrderedCollection`、FEP-171b） | `https://3ch.io/ap/t/{bbs}/{key}` | レス一覧を返す |
| >>1（スレ立て） | `Page`（`name` = スレタイ）。Mastodon 向けには `Note` で `name` を本文先頭にも入れる | `https://3ch.io/{bbs}/{key}/1` | Lemmy 系は `Page` を投稿として扱う |
| >>2 以降 | `Note`。`inReplyTo` = >>1。本文中の最初の `>>n` があれば `>>n` を `inReplyTo` にする | `https://3ch.io/{bbs}/{key}/{n}` | スレは時系列でフラット。`>>n` の木構造は補助情報 |
| あぼーん | `Delete` → `Tombstone` | 同上 | 番号は詰めない（v5 と同じ） |
| スレスト / 1000 到達 | 何も送らない（後述の「書き込み不可」を `Group` 側の表示で示すだけ） | — | |
| 名前欄（識別 ID を含む）・メール欄 | `Note` の本文先頭に「名前 ◆トリップ (識別 ID)」を表示用に入れる。構造化データは拡張プロパティ（`ch3:` 名前空間）に | — | Mastodon は拡張を読まないので、本文に入れないと見えない |

- 本文は dat の HTML（`<br>`、アンカー）をそのまま使える。`>>n` は該当レスの URL へのリンクに変換する。
- 投稿の恒久 URL（`/{bbs}/{key}/{n}`）は **dat 落ちがない方針（`04_dat落ちを採用しない.md`）なので恒久にできる**。AP の `id` はこれを使う。
- スレ番号は 1000 / 2000（`05_最大レス数の検討.md`）で打ち止め。AP 側で `inReplyTo` が上限を越えることはない。

### 3.2 投稿者（匿名性とアクターの衝突）

AP の投稿は `attributedTo` に投稿者アクターを持つのが前提で、Lemmy などは `attributedTo` が `Person` でないと受け付けない。
匿名掲示板の「名無し」をどう表すかで案が分かれる。

| 案 | 内容 | 長所 | 短所 |
| :-- | :-- | :-- | :-- |
| A. 板アクターが全投稿の投稿者 | `attributedTo` = 板の `Group`（または板ごとの「名無しさん」`Person` 1 つ） | 単純。アクターが増えない | 全投稿が同一人物に見える。スレ内の識別 ID による見分けが消える。Fediverse 側で「名無しさん」をミュートすると板全体が消える |
| **B. 日替わりの識別 ID ごとの使い捨てアクター（推奨）** | `attributedTo` = `https://3ch.io/ap/a/{bbs}/{yyyymmdd}/{h}`。`h` は識別 ID 文字列のハッシュ（識別 ID は `.` や空白を含み、URL・ハンドルにそのまま使えないため）。`name` = 名前欄 + 識別 ID（既定「名無しさん (jp.xx.yy zz-…)」） | 3ch の「識別 ID で見分けるが翌日には追えない」性質をそのまま写せる。識別 ID は既に公開されている値なので新たな情報は漏れない | アクター文書をその場で生成する必要がある（保存は不要）。鍵の扱い（下記） |
| C. 投稿ごとに別アクター | 完全に追跡不能 | 匿名性が最も強い | スレ内の見分けも消え、3ch の文化と合わない |

- **識別 ID 無しのスレ・板**（SETTING コマンド、`BBS_ID_SHIKIBETSU=d` 相当）は、案 B が使えないので案 A（板の「名無しさん」）に落とす。
- 識別 ID の表示粒度を下げた板（`ken` / `as` など）では、同じ地域・回線の別人が同一アクターにまとまる。表示と同じ粒度で見分けるだけなので、これは許容する。
- **トリップ**: 本人が希望すれば固定アクター `@◆xxxxxxxx@3ch.io` にする（フォローされる / 通知を受けられる）。
  トリップは既に「匿名のまま同一人物を示す」仕組みなので、AP の固定アクターと相性が良い。
  ただしトリップの計算方式は変えない（`AGENTS.md` §3.4）。トリップ文字列が衝突・解読された場合の乗っ取りリスクは既存と同じ。
- **キャップ**: 運営・板主などの固定アクターにする。
- **鍵**: 使い捨てアクター自身は何も送信しない（配信は板アクターの `Announce` で行う）ので、送信用の署名鍵は本来いらない。
  ただし実装によっては公開鍵のないアクターを弾くため、FEP-521a の Ed25519 鍵をサーバーの秘密値から決定的に導出する案を検討する（保存不要・導出は軽い）。
  **主要実装（Mastodon / Misskey / Lemmy）が鍵なしアクターを受け付けるかは要検証。**

## 4. リアクション機能（Misskey 風機能の検討）

### 4.1 Misskey の機能の棚卸し

Misskey の主な機能を、3ch に入れるべきかで分類する。

| 機能 | 判定 | 理由 |
| :-- | :-- | :-- |
| **絵文字リアクション** | **入れる** | 「書き込むほどではないが反応したい」層を拾える。書き込みの心理的敷居が高い過疎板でも、反応が見えることで「人がいる」と分かる（クリティカルマス対策）。dat を汚さずに入れられる |
| カスタム絵文字 | 限定的に入れる | 運営が用意した固定セット + Unicode 絵文字の固定セットに限る。板主・利用者によるアップロードは審査コストが大きく、運営者不在で回らない |
| 引用（Renote / 引用 Renote） | 入れない | 3ch には `>>n` アンカーがあり、スレ外への引用は URL 貼り付けで足りる |
| 投票（アンケート） | 検討 | v3 に相当機能があれば要件候補。AP では `Question` で表現でき、Mastodon / Misskey とも互換 |
| CW（注意書き付きで本文を畳む） | 検討 | ネタバレ板などで有用。AP では `summary` + `sensitive` |
| MFM（装飾記法） | 入れない | 専ブラで表示できない。dat の本文互換を壊す |
| クリップ・お気に入り | ローカル機能として入れる（AP に出さない） | 利用者ごとの機能で、ブラウザ保存で足りる |
| アンテナ（キーワード監視） | ローカル機能として入れる | 同上。専ブラの NG / 抽出機能と同種 |
| 通知 | トリップ・キャップの固定アクター利用者のみ | 名無しには宛先がない |
| フォロー（人を） | 入れない（3ch 内では） | 匿名掲示板の文化と合わない。Fediverse 側からトリップアクターをフォローするのは可 |

### 4.2 リアクションの仕様（案）

- **対象**: レス単位。スレスト・1000 到達後のスレにも付けられる（書き込みではないため。ただし板の設定で止められる）。
- **匿名で付けられる。** アカウントは不要。重複防止は「そのレスに、その絵文字で、同じ投稿者が 2 回付けない」とし、
  投稿者の同一性は、v6 の書き込み認証のトークン（と認証時の端末フィンガープリント）で判定する。
  識別 ID の計算とは別のソルトで別のハッシュを作り、識別 ID と突き合わせられないようにする（誰がどのリアクションを付けたか推測できないようにする）。
- **1 人が付けられる数**: 1 レスにつき異なる絵文字を 3 個まで（FEP-c0e0 / Pleroma 型）。Misskey は 1 人 1 個だが、受信側では Misskey の 1 個も 1 票として数えるだけなので問題ない。
- **誰が付けたかは表示しない**（件数だけ）。Fediverse から来たリアクションも件数に合算する。外部アクターの一覧は出さない。
- **絵文字セット**: 固定の Unicode 絵文字（十数個程度）+ 運営のカスタム絵文字。板ごとに有効にするセットを選べる。
  セット外の絵文字が Fediverse から来た場合は「その他」に合算するか捨てる。
- **専ブラへの影響なし**: dat・subject.txt は一切変えない（`AGENTS.md` §3.4 の不変条件）。
  リアクションは別エンドポイント（JSON、UTF-8）で Web 版にのみ出す。専ブラ向けに出すかは将来の独自拡張として別途検討。
- **規制**: 投稿の規制（`moderation.js` の deny.cgi 相当）をリアクションにも適用する。レート制限は投稿より緩く、かつ別枠。
  リアクションでの荒らし（大量の否定的リアクション）対策として、否定的な絵文字はセットに入れない。
- **保存（Step 5）**: スレの SQLite 型 DO に `reactions(res_no, emoji, count)` と、重複防止用の
  `reaction_votes(res_no, emoji, voter_hash, created_at)` を持つ。スレ単位で閉じるので DO の分割と合う。
  レス 1 件あたり 1 リアクションで 2 行書き込み（投稿と同程度）。
- **Step 4 では入れない**（DB 変更なしの制約。v5 の Thread DO の KV に足すと KB-28 の容量問題を悪化させる）。

### 4.3 AP でのリアクションの送受信

- **受信**: `Like`（`content` に絵文字があればその絵文字、なければ既定の「いいね」）と `EmojiReact` を同じに扱う（FEP-c0e0 の要求どおり）。
  取り消しは `Undo`。Lemmy の `Dislike` は捨てる（否定的リアクションを持たない方針）。
- **送信**: 3ch 内のリアクションを外部に送るかは、送り主のアクターがないので原則送らない。
  レスの `likes` / リアクション件数をオブジェクトに載せて、取得した側が数を見られるようにする程度にとどめる。

## 5. 段階的な導入計画

| 段階 | 内容 | 前提 | 危険度 |
| :-- | :-- | :-- | :-- |
| P0 | 3ch 内のリアクション（AP なし） | Step 5 の DB | 低 |
| P1 | 板の `Group` を公開し、**新スレだけ**を配信（読み取り専用） | 投稿の恒久 URL、配信キュー（bg） | 低 |
| P2 | レスも配信（板ごとに「新スレのみ / 全レス」を選択）。FEP-171b / f228 でスレ全体を取得可能に | P1 | 低〜中（配信コスト） |
| P3 | 外部からのリアクションを受信 | P0, P1。受信箱（inbox）と署名検証 | 中 |
| P4 | 外部からのリプライを取り込み、スレのレスとして dat に載せる | 自動モデレーションの完成、下記 5.1 | **高** |
| P5 | 外部から板宛てに投稿してスレ立て（NodeBB の方式） | P4 | 高 |

### 5.1 外部からの書き込み（P4）の論点

- **dat への載せ方**: 名前欄に `名無し@misskey.io` のように元サーバーを入れる、識別 ID 欄は元アクターのハッシュから作る、など。
  dat の 5 フィールド構造は変えずに表現できる。
- **文字コード**: 外部の本文は UTF-8。JIS X 0208 外の文字（絵文字など）の扱いは、Web 版からの投稿と同じ既存の変換規則に従う（`docs/sjis差異一覧.md`）。
- **検証順序**: 3ch への書き込みと同じパイプライン（NG ワード、規制、本文長）に通す。エラー時は AP 側に何も返さず捨てる（返す手段がない）。
- **規制の単位**: IP が取れないので、サーバー単位・アクター単位で規制する。サーバーのブロックリスト（defederation）を管理画面に置く。
- **荒らし**: Fediverse 経由のスパムは実際に大規模に起きている（2024 年の Mastodon スパム波など）。
  3ch 側の自動化（KSF 2）が完成する前に開けると、運営者不在時に止められない。**避難モード中は P4 を自動で止める**。
- **責任の所在**: 外部投稿の発信者情報は元サーバーにしかない。開示請求への対応手順（元サーバーへの照会先の記録）を先に決める。

## 6. 法務・運用上の注意

- **消しきれない**: `Delete` を送っても、受信側が消す保証はない。削除依頼で消したレスが他サーバーに残りうる。
  - 対策: 連合は板ごとのオプトイン、投稿フォームに「この板の書き込みは Fediverse に配信されます」と明示する、
    配信を遅らせて（例: 数分〜数十分）、その間の削除は配信前に取り消す。
- **成人向け・グレー領域の板は連合しない**（企画書「ドメインごと分離」と整合）。連合する場合も `sensitive` を付ける。
- **誹謗中傷系スレの再浮上**: 企画書の SEO と同じ配慮。古いスレの backfill（FEP-f228）には期間の上限を設ける。
- **検索避け**: Fediverse 側の全文検索で拾われることを嫌う板のために、`indexable: false`（Mastodon 拡張）を板ごとに設定できるようにする。
- **Fediverse の他サーバーからのブロック**: 匿名掲示板というだけでブロックされる可能性がある。サーバー規約・モデレーション方針を公開しておく（企画書「審査基準は最初から明文化して公開」）。

## 7. インフラ・コスト

- **配信（fan-out）**: 1 件の投稿を、フォロワーのいるサーバー数（共有受信箱ごとに 1 回）だけ送る。
  なんG型の避難イベント（1 日 1 万書き込み超）で全レス配信すると、フォロワーサーバー 100 なら 1 日 100 万リクエストになる。
  - **総合板は「新スレのみ」配信を既定にする。** 全レス配信は専門板（低頻度）向け。
  - 配信は Cloudflare Queues + bg で非同期に行い、投稿の応答時間に影響させない。失敗時は指数バックオフで再送し、長期不達のサーバーは配信先から外す。
- **受信箱（inbox）**: HTTP Signatures（draft-cavage 系と RFC 9421 の両方）を検証する。検証のための外部アクター取得はキャッシュする（KV）。
  受信は Workers で受け、処理は Queue に積む。
- **実装基盤**: Step 3 は Scala.js + HonoX。AP 部分は TypeScript の Fedify（Cloudflare Workers 対応）を HonoX 側で使う案と、
  Scala.js で自前実装する案がある。署名・JSON-LD・各実装の癖への対応量を考えると Fedify の利用を第一候補とし、
  Scala↔TS の境界型の制約（`../ch3s-migration/GEMINI.md`）の中で組めるかを P1 着手時に確認する。
- **DO の起動**: 外部からのオブジェクト取得（`GET /{bbs}/{key}/{n}` を `Accept: application/activity+json` で）は、
  休眠中のスレでも DO を起こさず返せるようにしたい（企画書「休眠板でも静的に読める経路」と同じ要件）。

## 8. 不可逆な設計判断（Step 5 の DB 設計前に決める）

方針企画書の「不可逆な設計判断チェックリスト」に追加する候補:

- [ ] **投稿の恒久 URL** `/{bbs}/{key}/{n}` を決め、以後変えない。AP の `id` はこれを使い、一度配ったら変更できない。
- [ ] **AP で使うドメイン**を決める。AP のアクター・オブジェクトの ID はドメインを含み、ドメインを変えると連合が切れる。
      `Person` には `Move` による引っ越しがあるが、`Group`（板）の引っ越しは標準化されていない。
      企画書の「ドメインを差し替え可能にする」（KSF 4）と正面から衝突するため、
      **AP 専用に長期保持できるドメイン（レジストラリスクの低いもの）を分ける**か、ドメイン変更時は連合をやり直す前提にするかを決める。
- [ ] **リアクションの保存場所**を Thread DO（SQLite）に確保する（4.2）。
- [ ] **使い捨てアクターの URL の作り方**（3.2 案 B）。識別 ID の計算式を変えると過去のアクター URL が壊れるので、識別 ID の計算仕様（v6 の端末フィンガープリント込み）と一緒に固定する。
- [ ] **bg の配信キュー**の枠をとっておく（P1 以降で使う）。
- [ ] リアクションの重複判定に使うハッシュのソルトを、識別 ID 用とは別に用意する。

## 9. 未決事項

- Misskey から `Group` をフォローしたときの表示（Misskey の Group 対応は限定的）。Misskey 利用者が多いので、
  板アクターを `Group` ではなく `Service` や `Person` にする代替も含めて検証する。

- リアクションを専ブラ向けに出すか（独自拡張ヘッダ・別ファイルなど）。
- 外部からの書き込み（P4）を将来的にも入れるかどうか。入れない場合、3ch は「Fediverse に配るが受け取らない」サイトになる。
