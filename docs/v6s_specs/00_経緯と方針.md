# 00. 3ch システムの経緯と v6 の進め方

Step 4 / 5 の仕様検討の前提として、これまでの世代（v3〜v5）の経緯と、v6 をどの順序で作るかをまとめる。
課題の詳細は `01_現行v5の課題.md` を参照。

---

## 1. 世代ごとの経緯

| 世代 | 時期 | 概要 |
| :-- | :-- | :-- |
| v3 | 2021〜 | `bbs18c` をベースに改修を続けたもの。ベースは 2000 年代の PHP 5 系、フロントも jQuery 1 系のレガシー構成。 |
| v3（新仕様化） | 2022-08〜10 | `bbs.cgi` を中心に全面改修した。記録方式の変更（`.dat` → `.cgi`）、認証の導入、規制の全面見直しなど。 |
| v3（規制文言変更） | 2023-03〜06 | 規制文言を変更した。 |
| v4（`delightly-v2`） | — | v3 の仕様を再検討しつつ、PHP 7 系で書き直したもの。 |
| v5（`ch3s`, 現行） | — | 3ch を Cloudflare Workers で動かすことになった際に、短期間で作ったもの。 |

## 2. 評価

- v3 / v4 は、設計・実装はひどいが、**利用者からの評判は良かった**。
- v5 は、昔の 2ch と同じ程度の機能しかない最低限の実装で、そのうえ不具合もある。そのため UX が低い。
  - 設計・実装も悪く、改善や将来の拡張に耐えられそうにない。
  - v3 の機能を忠実に移植できていない。これが、現在の 3ch に人が集まらない要因につながっている。

## 3. 進め方

v3 をそのまま移植するのは難しく、微妙でもある（現実的ではない）。
そこで、次の順序で進めるのが妥当と判断した。

1. **v5 を仕様そのままでリプレイスする**（ロードマップ Step 3: Scala.js + HonoX）。
2. **既知不具合を修正する**（`docs/既知不具合台帳.md` の KB-nn）。
3. **v3 を参考に機能を追加・拡張する（新仕様化）**（Step 4 フロント / Step 5 バックエンド + bg）。
4. **過去ログを投入する**（Step 6）。

### ロードマップ（`AGENTS.md` §2）との対応

| 本方針 | AGENTS.md | 備考 |
| :-- | :-- | :-- |
| ① 仕様そのままでリプレイス | Step 3 | バイト単位で同一の出力を差分テストで確認する |
| ② 既知不具合の修正 | Step 3 完了後（§3.3「修正に着手してよいのは step 3 完了後」） | ロードマップ上に独立した Step はない |
| ③ v3 を参考に新仕様化 | Step 4, 5 | v3 は「そのまま移植」ではなく、機能の参考元として扱う |
| 過去ログ投入 | Step 6 | |

### Step 4 / 5 の検討への含意
- 「v3 にあった機能」は、そのまま再現する対象ではなく**要件の候補**として扱う。
  v3 の実装（PHP 5 系）の構造は引き継がない。
- 利用者に好評だった点（v3 / v4 の独自 JS による多機能な Web 版、SETTING コマンド、認証、規制）を優先して棚卸しする。
- v3 の 2022 年の新仕様化（認証導入・規制見直し）と 2023 年の規制文言変更が、認証・規制の要件を洗い出すときの主な参照先になる。

## 4. 仕様検討の指針

Step 4 以降の仕様は、**`docs/方針企画書_板戦略・広告戦略.md`（3ch の生存戦略）に照らして判断する**。
目的は広告収益の最大化ではなく**生存確率の最大化**であり、とくに次の点を仕様検討の判断基準にする。

- **運営者が動かなくても死なない設計**: モデレーションの自動化、板の生成・休止の自動化、放置されても数年もつインフラ、無視できるコスト。
- **KSF の優先順**: 板単位のクリティカルマス → 荒らし・スクリプト対策の自動化 → 1 投稿あたりの限界費用の最小化 → インフラの主権と可搬性 → 互換エコシステムとの接続 → 法的耐性。
- **不可逆な設計判断チェックリスト**（企画書の同名の節）は、Step 5 の DB・ストレージ設計より前に決着させる。
