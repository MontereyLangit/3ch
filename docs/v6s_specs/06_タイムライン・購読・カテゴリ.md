# 06. トップページのタイムライン・板の購読・カテゴリ（Workers AI による自動分類）

2026-09-26 検討開始（利用者からの要望）。同日、Step 4 での先行提供・カテゴリの統合方針・板作成者によるカテゴリ作成・購読設定の保存先などを決定（末尾「決定事項」）。

要望:
- トップページに、全板の新着レス一覧（タイムライン）を出す。
- 板を購読（フォロー）できるようにする。
- 板を Cloudflare Workers AI で自動的にカテゴリに分ける。**購読・非表示はカテゴリ単位でもできるようにする。**
- カテゴリの初期値は旧 3ch（3ch.jp）の板一覧を使う。後からカテゴリを追加できるようにする。
  追加するのは**利用者（板作成者）**で、板作成時のカテゴリ登録で既存カテゴリから選ぶか、新しく作る。

## 結論

| 機能 | Step 4（DB 変更なし） | Step 5（DB 変更あり + bg） |
| :-- | :-- | :-- |
| タイムライン | **出す**（2026-09-26 決定）。簡易版: `headline.txt` から「板ごとの最新 age 書き込み」を並べる | 本版: レス単位の新着一覧（sage を含む）。投稿を Queue 経由で D1 に索引する |
| 購読・非表示（板単位 / カテゴリ単位） | **出す**（2026-09-26 決定）。ブラウザの `localStorage` に保存する | 同じ。**認証が入った後もサーバーには保存しない**（2026-09-26 決定）。端末間の引き継ぎはクライアント側の手段で行う（3.4） |
| カテゴリ | 初期値（`data/categories_seed.json`）をフロントに同梱し、読み取り専用で使う | D1 の板マスタ + カテゴリ表に移す。板作成者が板作成時に選択・新規作成できる（1.3）。管理者は統合・廃止などで整理する |
| Workers AI による自動分類 | なし | bg で実行する。人が決めた分類は上書きしない |
| bbsmenu | 変えない（`03_管理画面・bgの画面方針.md` 5 章） | カテゴリを見出しにして生成する |

- 投稿パイプライン（`bbs.cgi`）の応答とレイテンシには手を入れない。索引は投稿の保存が終わった後に非同期で作る。
- 専ブラ向けの出力（dat・subject.txt・Shift_JIS）は変えない。タイムライン・カテゴリの API は Web 版専用の UTF-8 JSON とする。
- AI の分類結果は「推定」として扱う。人（管理者・板作成者・シード）が決めた分類が常に優先し、AI が止まっても板の作成・投稿・閲覧には影響しない。

## 1. カテゴリ

### 1.1 初期値（シード）
利用者から提供された旧 3ch の bbsmenu を、`data/categories_seed.json` に構造化した。

- カテゴリ 36 個、板 206 件（重複を除くと 201 板）。カテゴリ名は元の `<B>` 見出しから `@3ch` を除いたもの。
- `id` は ASCII のスラッグ（`chat`, `news`, `topic-chat`, …）。購読設定はこの `id` で参照するので、**`id` は一度決めたら変えない**（カテゴリ名は変えてよい）。
- 板は `bbs`（ディレクトリ名）で現行の板と突き合わせる。旧サブドメイン（`news.3ch.jp` など）は使わない。
- `title` は参考用。板名の正は各板の `SETTING.TXT` の `BBS_TITLE`。

元の一覧の注意点（シードでは元の構成のまま残した）:

| 内容 | 扱い |
| :-- | :-- |
| 1 つの板が複数のカテゴリに載っている（`chugaku` ×3、`koko` / `campus` / `newsvip` ×2） | **板とカテゴリは多対多**として設計する（1.2） |
| 同じ板で表記が違う（中学生 / 中学校、高校生 / 高校、大学生活 / 大学・短大、ﾆｭｰ速VIP / ニュー速VIP） | 板名は `BBS_TITLE` を使うので問題にならない |
| 「小学生」が外部サイト（`www.10ch.net/bbs/`） | `external` として記録した。3ch の板ではないので、突き合わせの対象外 |
| 「既婚@3ch@3ch」 | 元の表記の誤りと思われる。`title` は「既婚@3ch」のまま（参考表示用） |
| 「雑談」と「雑談2」 | **まとめない**（2026-09-26 決定）。「雑談」はラウンジなどの一般雑談系、「雑談2」は VIP などの系統として分ける |
| 地域の 7 カテゴリ（北海道・東北〜九州・沖縄） | **統合しない**（2026-09-26 決定）。将来、市区町村単位の板ができる場合にも、地方のカテゴリの下に板が増えるだけで済むようにする |
| 現行の 3ch に存在しない板 | シードの行はそのまま残す。同じ `bbs` の板が作られた時点でそのカテゴリに入る（Step 6 の過去ログ投入とも整合する） |

現行の板一覧（`headline.txt` / 板マスタ）との突き合わせはまだしていない。Step 5 のデータ投入時に、シードにない現行板を洗い出して AI 分類の対象にする。

### 1.2 データモデル（Step 5、D1）

```sql
CREATE TABLE categories (
  id            TEXT PRIMARY KEY,           -- スラッグ。変更不可
  name          TEXT NOT NULL,              -- 表示名。Shift_JIS（JIS X 0208）で表せる文字だけ
  sort          INTEGER NOT NULL,
  status        TEXT NOT NULL,              -- active | proposed（AI の提案。管理者の承認待ち）| retired
  listed        INTEGER NOT NULL DEFAULT 1, -- bbsmenu・板一覧に見出しとして出すか（1.4）
  origin        TEXT NOT NULL,              -- seed | admin | creator（板作成者）| ai
  created_by_bbs TEXT,                      -- origin=creator のとき、作成の契機になった板
  merged_into   TEXT REFERENCES categories(id), -- 統合したときの行き先（購読設定の移し替えに使う）
  default_hidden INTEGER NOT NULL DEFAULT 0,  -- 既定でタイムラインに出さない（例: 運営）
  description   TEXT,                       -- AI 分類のヒント。任意
  created_at    INTEGER NOT NULL
);

CREATE TABLE board_categories (
  bbs           TEXT NOT NULL,
  category_id   TEXT NOT NULL REFERENCES categories(id),
  source        TEXT NOT NULL,              -- admin | creator | seed | ai
  confidence    REAL,                       -- source=ai のときだけ
  model         TEXT,                       -- source=ai のときだけ。分類に使ったモデル
  is_primary    INTEGER NOT NULL DEFAULT 0, -- 1 板につき 1 つ。Web 版の板一覧で主に出す見出し
  updated_at    INTEGER NOT NULL,
  PRIMARY KEY (bbs, category_id)
);
```

- 板マスタ（`01_現行v5の課題.md` 7 章。状態・最終書き込み時刻など）とは `bbs` で結ぶ。カテゴリを板マスタの列にしないのは、多対多のため。
- どのカテゴリにも入っていない板は「未分類」とする（表示上は「その他」）。

### 1.3 カテゴリの追加（板作成者）
**カテゴリを追加するのは利用者（板作成者）**とする（2026-09-26 決定）。ユーザーによる板作成（方針企画書「ユーザーによる板作成機能が構造的優位を生む」）の画面に、カテゴリ登録の欄を設ける。
板作成と同じく Step 5 で出す（今の板作成は管理画面の `/admin/make` だけで、カテゴリの保存先もない。`03_管理画面・bgの画面方針.md` 2 章）。

板作成時のカテゴリ登録は**任意**で、1 板あたり **0〜2 個**（既存から選んだものと新しく作ったものの合計）とする（2026-09-26 決定）。

| 操作 | 内容 |
| :-- | :-- |
| 既存から選ぶ | `active` のカテゴリから選ぶ。`board_categories` に `source=creator` で入る |
| 新しく作る | 名前を入れて作る。`origin=creator`, `status=active` で即時に作られ、作った板がそのカテゴリに入る |
| 選ばない（0 個） | 可。選ばなかった板は AI 分類の対象になる（2 章） |

新しく作るときの検査（板作成と同じ送信の中で行う）:
- 名前は Shift_JIS（JIS X 0208）で表せる文字だけ。bbsmenu の見出しにそのまま出るため。**最大 20 文字**（2026-09-26 決定）。
- NG ワード（`ngwords.cgi`、Step 5 以降は後継の規制）で弾く。
- 既存カテゴリとの重複は、**名前が完全に一致する場合だけ**とする（表記ゆれは同じ名前とみなさない。2026-09-26 決定）。
  完全一致なら新規作成せず、その既存カテゴリを選んだ扱いにする。全角 / 半角・大文字 / 小文字などの違いは別のカテゴリになる。
  表記ゆれで重複したカテゴリは、管理者が事後に統合する（1.4）。
- `id` は利用者に入力させず、システムが採番する（例: `u-` + 連番の 36 進）。`id` は変更不可なので、名前の打ち間違いを直しても購読設定は切れない。
- 板作成の摩擦（実績条件・避難モード。方針企画書）がそのままカテゴリ作成の摩擦になる。カテゴリだけを作る操作は設けない。

### 1.4 乱造・荒らしへの備え
板作成者が自由にカテゴリを作れるため、次の仕組みで一覧が荒れないようにする。

- **見出しに出すのは、正式板を 1 つ以上含むカテゴリだけ**（`listed` を bg が更新する）。仮設板だけのカテゴリは、板一覧・bbsmenu の見出しに出さない（板のページとカテゴリのページには出す）。
  方針企画書の板ライフサイクル（仮設板 → 正式板）に合わせ、定着した板があるカテゴリだけが一覧に残る。
- 所属する板がすべて休止・アーカイブ・削除になったカテゴリも見出しから外す（データは消さない）。
- 管理者はカテゴリ管理（仮 URL `/admin/categories`、Step 5。v6 モックには未掲載）で事後に整理する。

| 管理者の操作 | 内容 |
| :-- | :-- |
| 名前・並び順の変更 | `id` は変わらないので購読設定に影響しない |
| 統合 | `merged_into` を設定し、所属する板を統合先に移す。重複カテゴリの整理に使う。クライアントは購読設定を読むときに `merged_into` をたどって読み替える |
| 廃止 | `status=retired`。所属する板が他のカテゴリに入っていなければ未分類になり、AI 分類の対象に戻る |
| 板の割り当て | 板管理（`/admin/boards/`）から、板ごとにカテゴリを付け外しする。`source=admin` になり、板作成者の選択より優先する |
| 追加 | 管理者も作れる（`origin=admin`）。シードにないカテゴリを先に用意する場合など |
| AI 提案の承認 | `status=proposed` のカテゴリを承認すると `active` になる（2.3） |

## 2. Workers AI による自動分類（Step 5、bg）

### 2.1 優先順位
1. `source=admin`（管理者が付けたもの）
2. `source=creator`（板作成者が板作成時に選んだもの・作ったもの）
3. `source=seed`（提供された一覧）
4. `source=ai`

シードにある `bbs` の板を新しく作った場合でも、板作成者がカテゴリを選んだならそちらを使う（シードの行は、作成者が選ばなかったときだけ使う）。

AI は、**人（admin / creator / seed）の割り当てがない板だけ**を分類する。人の割り当てを AI が書き換えたり外したりすることはない。
管理者が AI の割り当てを外した場合は、同じ板に同じカテゴリを AI が付け直さないよう、「付けない」印（`source=admin` の否定行、または別表）を残す。細部は実装時に決める。

### 2.2 いつ分類するか
- 板が作られ、板作成者がカテゴリを選ばなかったとき。
- 未分類の板があるとき（bg の定期実行、例: 1 日 1 回）。
- AI が付けた板の見直し（例: 月 1 回）。「生える板」は立てた時と中身が変わるため。
- カテゴリが追加されたとき（未分類の板と、AI が付けた板だけを再分類する）。
- 管理画面の「再分類」ボタン。

投稿のたびには実行しない。投稿パイプラインには AI の呼び出しを入れない（KSF「1 投稿あたりの限界費用の最小化」）。

### 2.3 入力と出力
入力（板ごと）:
- `BBS_TITLE`
- `head.txt`（HTML タグを除き、先頭 1,000 文字程度）
- `subject.txt` の上位 30 スレのタイトル

レスの本文は入れない。費用・プライバシー・プロンプトインジェクションの面を小さくするため。

呼び出し:
- カテゴリ一覧（`active` の `id` / 名前 / `description`、代表的な所属板名）をプロンプトに入れ、その中から最大 2 つを選ばせる。36 カテゴリ程度なら 1 回の呼び出しに収まる。
- JSON Schema 付きの出力（Workers AI の JSON Mode）で、`{"categories":[{"id":"…","confidence":0.0}], "suggestion":"…"}` の形に固定する。温度は 0。
- モデルは実装時に選ぶ。候補は Workers AI の日本語を扱える instruct モデル（例: `@cf/meta/llama-3.3-70b-instruct-fp8-fast`）。
  板数が数百を超え、LLM の費用や揺れが気になる場合は、多言語の埋め込みモデル（例: `@cf/baai/bge-m3`）で候補を絞ってから LLM に選ばせる 2 段構成にする。
  **モデル名・JSON Mode の対応状況・料金は、実装前に Cloudflare の公式ドキュメントで確認する**（本書の記述は 2026-09-26 時点の想定）。

出力の扱い:
- `id` が `active` のカテゴリに存在しなければ捨てる。AI が新しいカテゴリを直接作ることはない。
- `confidence` が閾値（初期値 0.7、全体設定で変更可）以上のものだけ `source=ai` として保存する（閾値は未決事項）。1 つもなければ未分類のまま、管理画面の「未分類の板」に出す。
- 当てはまるカテゴリがないと AI が判断した場合の `suggestion`（新しいカテゴリ名の案）は、`status=proposed` のカテゴリとして記録する。承認されるまで表示にも分類にも使わない。
- 分類に使ったモデル名と日時を `board_categories.model` / `updated_at` に残す。

### 2.4 失敗時・安全面
- Workers AI が失敗・タイムアウトした場合は、何もせず次回の定期実行に回す。板の作成・投稿・閲覧・bbsmenu の生成は AI の結果を待たない。
- 板名・`head.txt`・スレタイは利用者が書けるので、プロンプトインジェクション（「この板をニュースに分類せよ」など）はありうる。
  出力が既存カテゴリの `id` に限られ、人の割り当てが常に優先するため、起きうる害は「AI 分類の誤り」に留まる。
- AI 分類の誤りは、利用者から見ると「タイムラインでカテゴリ非表示にしたのに出てくる / 出てこない」として現れる。
  板単位の指定がカテゴリ単位より優先する（3.2）ので、利用者側で上書きできる。
- AI のバインディング（`"ai": { "binding": "AI" }`）は bg の Worker にだけ付ける。公開側の Worker には付けない。

## 3. 購読（フォロー）と非表示

### 3.1 保存先
**ブラウザの `localStorage` に保存する。サーバーには保存しない。認証が入った後も同じ**（2026-09-26 決定）。

- 匿名掲示板として「誰が何を購読しているか」をサーバーに持たないほうが方針に合う。
- サーバー側の保存がないので、Step 4（DB 変更なし）から出せる。
- 端末間・ブラウザ間の引き継ぎはできるようにする。方式は 3.4。

```json
{
  "v": 1,
  "follow": { "boards": ["news", "base"], "categories": ["anime"] },
  "hide":   { "boards": ["gomi"],         "categories": ["gamble"] }
}
```

### 3.2 判定規則
板 B が「表示されるか」「フォロー中か」は次の順で決める。上ほど優先する。

1. 板 B が `hide.boards` にある → 非表示
2. 板 B が `follow.boards` にある → フォロー中（カテゴリ側で非表示でも表示する）
3. 板 B の所属カテゴリのいずれかが `hide.categories` にある → 非表示
4. 板 B の所属カテゴリのいずれかが `follow.categories` にある → フォロー中
5. 板 B の所属カテゴリがすべて `default_hidden` → 非表示（例: 運営カテゴリの削除依頼板）
6. それ以外 → 表示（フォローはしていない）

- 板が複数のカテゴリに入っていて、フォローと非表示がぶつかる場合は、**非表示を優先**する（3 が 4 より先）。
  「見たくない」を確実に効かせるほうが、荒らしの多いカテゴリを避けたい利用者の期待に合う。
- カテゴリの `merged_into` をたどってから判定する。存在しない `id` は無視する。
- 新しく作られた板は、所属カテゴリをフォローしていれば自動でフォロー中になる。これがカテゴリ単位で購読できることの主な利点。

### 3.3 画面
- 板一覧: カテゴリを見出しにして並べ、見出しと各板に「フォロー / 非表示」の切り替えを付ける。並び順は直近のアクティビティ順を既定にする（方針企画書「全板一覧を墓場に見せない」）。
- タイムライン: 「すべて」（非表示を除く全板）と「フォロー中」の 2 つのタブ。
- 各レス・板の見出しから、その場で「この板を非表示 / このカテゴリを非表示」を選べるようにする。

### 3.4 引き継ぎ（エクスポート / インポート）
サーバーを経由しない方法で、設定を別の端末・ブラウザに移せるようにする。

| 方式 | 内容 |
| :-- | :-- |
| 引き継ぎコード | 設定（3.1 の JSON）を圧縮して base64url にした文字列。コピーして、移行先の設定画面に貼り付ける |
| ファイル | 同じ内容を JSON ファイルとして保存・読み込みする。バックアップにも使える |
| QR コード | 引き継ぎコードを QR コードで表示し、スマートフォンのカメラで読み取って移行先で開く（URL のフラグメント `#import=…` に入れ、サーバーにはリクエストとして送らない） |

- 取り込むときは「置き換える」か「今の設定に足す」かを選ばせる。足す場合、同じ板・カテゴリがフォローと非表示の両方に入ったら、取り込む側を優先する。
- 形式に版番号（`"v": 1`）を持たせ、古い版のコードも読めるようにする。存在しない板・カテゴリの `id` は取り込んだうえで無視する（3.2）。
- 引き継ぎコードに個人を特定できる情報は入らない（購読と非表示の一覧だけ）。
- サーバーで一時的に預かる方式（短いコードを発行して移行先で入力する等）は、サーバー保存にあたるので採らない。

## 4. タイムライン（全板の新着レス一覧）

### 4.1 Step 4: `headline.txt` を使う簡易版
今の DB で出せる範囲。管理用 API と同様に、読み取りの API を追加して Next.js から使う。

- 元データは `headline.txt`（`bbs.cgi.js` の `updateHeadline`）: 1 板につき「最後の age 書き込み」1 件、最大 300 板、本文の先頭 30 文字。
- **sage の書き込みは出ない**（`bbs.cgi.js:841`）。「新着レス」ではなく「板の新着」として見せる。
- 削除済みのスレは除く（`/headline/subject.txt` と同じく `Board.getRemoved()` で除外、`main.js:148`）。
- 購読・非表示の判定（3.2）はクライアントで行う。

### 4.2 Step 5: レス単位の本版

```
bbs.cgi（保存成功後） --ctx.waitUntil--> Queue --> bg（consumer, バッチ）--> D1 timeline_posts
Web 版 --> GET /api/timeline --> D1（エッジキャッシュ 5 秒程度）
```

- 投稿の保存が成功した後に、`ctx.waitUntil` で Queue にイベントを送る。投稿の応答内容・順序は変えない。
  Queue への送信が失敗しても投稿は成功扱いのまま（タイムラインに出ないだけ）。
- bg がイベントをまとめて D1 に書き込む。避難イベント時（1 日 1 万書き込み超）でも、バッチで書けば D1 の書き込み回数は抑えられる。

```sql
CREATE TABLE timeline_posts (
  bbs          TEXT NOT NULL,
  thread_key   TEXT NOT NULL,
  res_no       INTEGER NOT NULL,
  posted_at    INTEGER NOT NULL,
  thread_title TEXT NOT NULL,
  excerpt      TEXT NOT NULL,   -- 本文の先頭 60 文字程度（仮値。未決事項）。タグ・アンカーを除いたプレーンテキスト
  PRIMARY KEY (bbs, thread_key, res_no)
);
CREATE INDEX timeline_posts_time  ON timeline_posts (posted_at DESC);
CREATE INDEX timeline_posts_board ON timeline_posts (bbs, posted_at DESC);
```

- 名前・トリップ・ID・IP・投稿者ログは入れない。タイムラインは入口で、中身はスレで読む。
- 保持期間は 7 日程度（仮値。未決事項）とし、bg が古い行を消す（タイムラインは過去ログではない）。

API（UTF-8 JSON、Web 版専用）:

| API | 内容 | キャッシュ |
| :-- | :-- | :-- |
| `GET /api/timeline?before=&limit=` | 全板の新着 | 全員共通なのでエッジで数秒キャッシュできる。「すべて」タブはこれを取り、クライアントで非表示を除く |
| `GET /api/timeline?bbs=a,b,c&before=&limit=` | 指定した板の新着（最大 50 板程度） | 板の並びを正規化（ソート）してキャッシュキーにする。「フォロー中」タブで使う |
| `GET /api/categories` | カテゴリ一覧と板の所属 | 変更時まで長めにキャッシュ |

- 購読の情報はクエリ（板の列）としてだけ送り、サーバーには残さない。
- 「すべて」タブで非表示が多く 1 ページが空に近いときは、クライアントが数ページまで続けて取る。

### 4.3 荒らし・削除との関係
タイムラインは、1 つの板の荒らしを全板の利用者に見せる増幅器になりうる。

- **スレ単位でまとめて表示する**: 同じスレの新着は「最新レス 1 件 + 新着 n 件」の 1 行にまとめる。連投で一覧が埋まるのを防ぐ。
- 板ごとに「タイムラインに出さない」設定を持つ（板マスタの列。Step 5）。カテゴリの `default_hidden` と合わせて、運営系・荒れやすい板を既定で外せる。
- あぼーん・スレ削除・スレスト・移転のとき、管理 API は `timeline_posts` の該当行も消す（または Queue に削除イベントを送る）。
  あわせて、読み出し時にも `Board` の `removed` を見て除く（Step 4 と同じ二重の防御）。
- 規制・NG ワードで拒否された投稿は保存されないので、Queue にも入らない。
- 成人向けの板はドメインごと分ける方針（方針企画書のチェックリスト）なので、このタイムラインには載せない。

## 5. bbsmenu との関係

`03_管理画面・bgの画面方針.md` 5 章で、bbsmenu は板マスタからシステム側で生成すると決めた。Step 5 ではカテゴリを見出しに使う。

- 形式は今の bbsmenu と同じ（`<B>カテゴリ名</B><BR>` の下に `<A HREF=…>板名</A><br>`）。専ブラの bbsmenu 解析と互換を保つ。
- 板は所属するすべてのカテゴリの下に出す（元の一覧と同じ）。未分類の板は「その他」の下に出す。休止中の板は出さない。
- 見出しに出すのは `listed=1` のカテゴリだけ（1.4）。仮設板そのものを bbsmenu に出すかどうかは、板のライフサイクルの検討で決める。
- 出力は Shift_JIS。カテゴリ名を Shift_JIS で表せる文字に限る（1.3）のはこのため。
- 並び順はシードの `sort` を先に、板作成者が作ったカテゴリはその後ろに作成順で並べる（管理者が並び替えられる）。
- Step 4 の間は bbsmenu を変えない。

## 決定事項（2026-09-26）
- 簡易タイムライン（4.1）と `localStorage` の購読・非表示（3 章、シードのカテゴリ）は **Step 4 で先に出す**。
- 「雑談」と「雑談2」は**まとめない**。一般雑談系（ラウンジなど）と VIP などの系統を分けるため。

- カテゴリを追加するのは**利用者（板作成者）**。板作成時のカテゴリ登録で、既存カテゴリから選ぶか、新しく作る（1.3）。
- 板作成時のカテゴリ登録は**任意**。1 板あたり **0〜2 個**（1.3）。
- カテゴリ名は**最大 20 文字**。重複とみなすのは**完全一致だけ**で、表記ゆれは同じ名前とみなさない（1.3）。
- 購読・非表示の設定は、認証が入った後も**サーバーに保存せずクライアント側で持つ**。引き継ぎは引き継ぎコード・ファイル・QR コードで行う（3.4）。
