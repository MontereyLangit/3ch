# 02. 板の「休止」は必要か（コスト面・実装面の検討）

`docs/方針企画書_板戦略・広告戦略.md` の板ライフサイクル（仮設板 → 正式板 → 休止 → アーカイブ）にある
「休止」を、コスト面と実装面から検討する。2026-09-25 検討。

## 結論

- **状態としての「休止」は採用する。** 板マスタに状態（正式・休止・アーカイブ）を持ち、一覧の見せ方と SEO の扱いに使う。
- **ストレージの退避（DO → R2、書き込み時に rehydrate）は、当面やらない。** 削れるコストがほぼ 0 なのに、実装が複雑になるため。
- 保存容量が数十 GB を超えたら、退避を検討し直す。

---

## 1. コスト面

Cloudflare 公式の料金ページ（2026-09-25 参照）による。いずれも Workers Paid プラン。

| 項目 | DO（SQLite 型） | DO（KV 型、v5 の現行 `new_classes`） | R2 Standard |
| :-- | :-- | :-- | :-- |
| 保存容量 | $0.20/GB-月（5 GB/月 まで無料） | $0.20/GB-月（1 GB まで無料） | $0.015/GB-月（10 GB-月 まで無料） |
| リクエスト | $0.15/100 万件（100 万件/月 まで無料） | 同左 | Class B（読み取り） $0.36/100 万件 |
| 実行時間 | $12.50/100 万 GB-s（40 万 GB-s/月 まで無料） | 同左 | — |

### 1.1 使われていない板の実行コストは、休止させなくても 0
- DO の実行時間は「JavaScript を実行中」か「hibernation の条件を満たさないアイドル中」だけに課金される。
  hibernation の条件を満たすオブジェクトは、実際に hibernate される前から課金されない。
- v5 の `Board` / `Thread` DO はタイマー・アラーム・WebSocket を使っていない（`src/durable_objects/*.js`）。
  そのため、書き込みのない板・スレは**今も実行コストがかかっていない**。

### 1.2 保存容量の差は月 1 ドル程度
- `kako-data` フォルダ全体の実測は 11 GB。バックアップ（`dat.bak-t245`）、`dat.zip`（136 MB）、変換作業用ファイル、他サイトのデータを含むので、実際に投入する量はもっと少ない。
- 多めに見て 11 GB 全部を DO に置いても、SQLite 型 DO で $1.20/月、R2 で $0.02/月（無料枠を引いた後）。差は月 1 ドル強。
- 過去ログは「スレ単位の過去ログ化」で R2 に置く想定なので、そもそも DO の容量には入らない。
- 休止中の板にクローラーが来て DO が起動しても、コストはリクエスト課金（$0.15/100 万件）と数十 ms の起動遅延だけ。

## 2. 実装面

ストレージを退避させる場合に必要になるもの:

- 休止に移す処理（bg または DO アラーム）と、書き込み時に DO へ戻す処理。
- 退避中・復元中に届いた書き込みの競合処理（R2 にはトランザクションがない。排他は DO が担っている）。
- 削除・移転・レス編集・`Range` / `304` など、スレを扱う全機能が「DO にある状態」「R2 にある状態」の両方で正しく動くこと。
- その全組み合わせのテスト。

v5 には似た仕組みがすでにある。旧形式ログ（`.cgi`）を読まれたときに DO へ移す処理（`thread.js:40-`）である。
この処理のために `legacyLog`、旧 DO キーからの引き継ぎ、移転処理の分岐などが増え、保守が難しくなっている。

企画書の「運営者が動かなくても死なない設計」「放置に数年耐えるインフラ」から見ても、仕組みの数を増やさないほうが方針に合う。

## 3. 退避しない場合の実現方法

企画書が「休止」に期待している効果は、退避しなくても得られる。

| 企画書の狙い | 実現方法 |
| :-- | :-- |
| 板一覧を「墓場」に見せない | 板マスタの状態で一覧から外す / 直近のアクティビティ順に並べる（`01_現行v5の課題.md` 7 章） |
| 休止中の板でも静的にクロールできる | エッジキャッシュ（Cache API / CDN）や SSR キャッシュから返す。DO が起動するかどうかと関係なく効く |
| 書き込みが再開したら復帰する（rehydrate-on-write） | 状態フラグを戻すだけ。データは動かさない |
| 容量が本当に増えたとき | スレ単位の過去ログ化（書き換わらない静的ファイルとして R2 に置き、CDN でキャッシュする）。既存の過去ログの仕組みの延長で済む |

## 4. 企画書の読み替え

企画書は受け取った原本なので書き換えない。本検討に合わせて、次のように読み替える。

- 状態遷移図の「無書き込み継続（DO hibernation→R2）」は、**「無書き込み継続（状態フラグを休止にする。データは動かさない）」**と読む。
  DO の hibernation はもともと WebSocket 向けの機能名で、書き込みのない DO はそれ以前に課金されない。
- 「休止 → 正式板: 書き込み再開（rehydrate-on-write）」は、**状態フラグを正式に戻すだけ**と読む。
- 不可逆な設計判断チェックリストの「休眠板（DO hibernation 中）でも静的にクロール・閲覧可能な読み取り経路」は、
  **「休止中の板でも、キャッシュ経由でクロール・閲覧できる読み取り経路」**と読む。

## 5. 退避を検討し直す条件

- DO に置くデータ量が数十 GB を超え、月額の差（$0.185/GB-月）が無視できなくなったとき。
  例: 100 GB で月 $18.5 程度。
- Cloudflare の料金体系が変わり、アイドル中の DO や DO の保存容量が高くなったとき。
