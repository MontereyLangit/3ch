# 既知不具合台帳（v5 → v6 移植）

**方針: 移植が完了するまで、ここに挙げた不具合は一切修正しない。記録のみ行う。**

Scala.js 移植（ロードマップ step 3）は現行 v5 の**バイト単位で同一な出力**を目標とする。
移植中にバグを直すと「移植の誤りによる差分」と「意図的な修正による差分」が混ざり、
検証が成立しなくなる。したがって不具合はキャラクタリゼーションテストで**現行の壊れた挙動のまま固定**し、
修正は移植完了後に、この台帳を起点として別途実施する。

- **記録先**: 本ファイル。新たに発見した不具合は下表に追記する。
- **固定先**: `tests/*.characterization.test.js`。各アサーションのコメントに `KB-xx` を記載して対応付ける。
- **修正時期**: step 3 完了（Scala.js 版が v5 と同一出力であることを確認）後。step 4 以降の新仕様検討に合わせて取り込む。

### 例外: 実際に悪用可能なセキュリティ欠陥

「移植まで修正しない」の唯一の例外。**現行本番環境で実際に悪用可能**なセキュリティ欠陥を見つけた場合は、
台帳に記録したうえで**利用者に報告し、先行修正するかどうかの判断を仰ぐ**。勝手に直さないが、黙って抱え込みもしない。
該当しうるもの: XSS、認証バイパス、任意コード実行、情報漏洩。
**現時点で該当するものは無い。** KB-22 は候補として検討したが、到達可能性を検証した結果、悪用不可と判断して通常扱いに戻した。

| 状態 | 意味 |

| 移植済 | Scala.js 版でも同じ挙動を再現できた |
| 修正済 | 移植完了後に修正した |

## 追記の作法

キャラクタリゼーションテスト作成中や移植中に新しい不具合を見つけたら、**修正せずに**次を行う:

1. 本表に `KB-nn` を採番して追記する（分類・現象・影響・対応方針・出典を埋める）。
2. 現行の壊れた挙動をテストで固定し、そのアサーションに `// KB-nn: <一行説明>` のコメントを付ける。
3. 仕様書（`docs/現行システム仕様書.md`）の記述と実動作が食い違っていた場合は、**コードの実動作を正として**仕様書側も訂正する。
